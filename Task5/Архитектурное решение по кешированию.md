# Задание 5. Кеширование

## Анализ системы для трейсинга

Анализ архитектуры показывает, что:
- MES хранит и обрабатывает большое количество заказов
- дашборд MES постоянно запрашивает список заказов по статусам
- данные часто читаются и относительно редко изменяются
- каждое обращение идёт напрямую в базу данных, которая обслуживает и чтение, и запись

Основной кандидат на кеширование - операции чтения:
- список заказов по статусам
- самые новые заказы
- справочные данные (статусы, параметры производства)

## Мотивация

Внедрение кеширования позволит:
- снизить нагрузку на базу данных MES
- ускорить загрузку дашборда операторов
- обеспечить приоритетный доступ к новым заказам
- стабилизировать время ответа системы при росте нагрузки
- подготовить архитектуру к масштабированию (в том числе в Kubernetes)

## Предлагаемое решение

### Тип кеширования

#### Серверное кеширование

Клиентское кеширование не подходит, так как:
- данные должны быть консистентны между операторами
- статус заказа может измениться в любой момент
- операторы конкурируют за одни и те же заказы

Серверное кеширование обеспечивает:
- единый источник актуальных данных
- контроль инвалидации
- централизованную бизнес-логику

### Технология кеша

Redis:
- in-memory
- высокая пропускная способность
- поддержка TTL и pub/sub
- хорошо интегрируется с C#, Java и Kubernetes

### Паттерн кеширования

#### Cache-Aside - основной паттерн.

Как работает:
1. MES запрашивает данные из Redis
2. Если данные есть - возвращаются из кеша
3. Если данных нет - запрос к БД, результат кладётся в кеш

Почему Cache-Aside:
- простая реализация
- гибкая инвалидация
- минимальные изменения в коде
- хорошо подходит для данных с частыми чтениями и редкими изменениями

Почему не Read-Through:
- логика загрузки данных переносится в слой кеша, что усложняет архитектуру
- сложнее контролировать бизнес-логику и инвалидацию на стороне приложения

Почему не Refresh-Ahead:
- увеличивается фоновая нагрузка на БД
- возможен лишний прогрев кеша

Почему не Write-Through:
- увеличивает задержки записи
- усложняет обработку ошибок

Почему не Write-Behind:
- асинхронная запись в БД создаёт риск потери данных при сбоях Redis
- для MES критична надёжность фиксации статуса заказа
- усложняется восстановление консистентности между кешем и БД
- повышаются требования к отказоустойчивости кеша (replication, persistence)

### Стратегия инвалидации кеша

#### Выбранная стратегия

Программная инвалидация + временная инвалидация

Комбинация программной + временной инвалидации обеспечивает оптимальный баланс между:
- консистентностью данных
- простотой реализации
- предсказуемостью поведения системы
- минимальными архитектурными рисками

Данная стратегия особенно хорошо подходит для сценария конкурентной работы операторов MES

#### Почему не другие стратегии
| Стратегия                       | Оценка                                                                                         |
| ------------------------------- | ---------------------------------------------------------------------------------------------- |
| Инвалидация на основе запросов  | Сложно формализовать, какие запросы считать триггером; высокая вероятность ложных срабатываний |
| Инвалидация на основе изменений | Требует отдельного слоя событий и усложняет архитектуру на текущем этапе                       |
| Инвалидация только по ключу     | Недостаточна для агрегированных представлений (списки заказов по статусам)                     |

## Альтернативные решения

### Сравнение решений

| Критерий               | Redis + Cache-Aside | Клиентское кеширование |
| ---------------------- | ------------------- | ---------------------- |
| Консистентность        | Высокая             | Низкая                 |
| Конкуренция операторов | Контролируемая      | Проблемная             |
| Нагрузка на БД         | Снижается           | Не снижается           |
| Масштабируемость       | Высокая             | Ограниченная           |
| Сложность              | Средняя             | Низкая                 |

Серверное кеширование с использованием Redis и паттерна Cache-Aside является оптимальным решением для MES. Оно решает текущие проблемы производительности, минимально вторгается в кодовую базу и масштабируется вместе с системой.
