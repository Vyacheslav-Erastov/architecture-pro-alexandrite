# Задание 4. Логирование

## Анализ системы и планирование логирования

### Какие логи необходимо собирать

#### Приоритетные системы

1. MES (C#) - основной узел бизнес-критичных операций
2. CRM (Java Spring Boot) - управление жизненным циклом заказа
3. RabbitMQ - точка потенциальной потери сообщений

Онлайн-магазин - во второй очереди, так как основные жалобы связаны не с созданием заказа, а с его дальнейшей обработкой

#### Обязательные бизнес-логи (уровень INFO)

| Событие                         | Поля                                                |
| ------------------------------- | --------------------------------------------------- |
| Создание заказа                 | order_id, source (B2C/B2B), timestamp               |
| Смена статуса заказа            | order_id, old_status, new_status, system, timestamp |
| Отправка сообщения в RabbitMQ   | order_id, exchange, routing_key, message_id         |
| Получение сообщения из RabbitMQ | order_id, queue, message_id                         |
| Начало расчёта стоимости        | order_id, polygon_count, timestamp                  |
| Завершение расчёта стоимости    | order_id, duration_ms, result                       |
| Взятие заказа оператором        | order_id, operator_id, timestamp                    |
| Ошибка бизнес-процесса          | order_id, error_code, description                   |

Все логи должны быть структурированными (JSON)

#### Другие уровни логирования

- WARN - деградации и аномалии (долгий расчёт, повторная обработка сообщения)
- ERROR - ошибки бизнес-логики, падения интеграций
- DEBUG - временно, только в dev/release окружениях

## Мотивация внедрения логирования

### Бизнес-эффекты

- снижение количества потерянных заказов
- уменьшение времени ответа поддержкой клиентам
- снижение оттока B2B-партнёров
- повышение прозрачности SLA производства

### Технические метрики, на которые влияет решение

- MTTR (Mean Time To Recovery)
- количество инцидентов без установленной причины
- процент заказов с "зависшим" статусом
- время расследования инцидента

## Предлагаемое архитектурное решение

### Выбор технологии

#### OpenSearch Stack
- OpenSearch (хранение и поиск логов)
- OpenSearch Dashboards
- Fluent Bit (агент сбора логов)

#### Причины выбора:
- open-source лицензия
- хорошая интеграция с Kubernetes и VM
- поддержка JSON-логов и алертинга

### Архитектура логирования

1. Все сервисы пишут структурированные логи в stdout / файл
2. Fluent Bit собирает логи с EC2-инстансов
3. Логи отправляются в OpenSearch
4. Для каждой системы отдельный индекс:
- logs-mes-*
- logs-crm-*
- logs-shop-*
- logs-rabbitmq-*

### Схема логирования

[Ссылка на доработанную диаграмму C4](./jewerly_c4_model_logs.drawio)

### Связь логов с трейсингом

В каждый лог добавляются:
- Trace ID
- Span ID
- order_id

Это позволяет коррелировать логи с трассами (из задания 3)

### Политика безопасности логов

Логи не должны содержать:
- персональные данные клиентов
- платёжную информацию
- содержимое 3D-файлов

Доступ:
- чтение логов - роли Support, DevOps, Backend
- запись - только сервисные аккаунты
- доступ через VPN / private network

Аудит доступа к OpenSearch включён

### Политика хранения логов

| Тип логов | Срок хранения | Причина             |
| --------- | ------------- | ------------------- |
| INFO      | 30 дней       | Оперативный анализ  |
| WARN      | 60 дней       | Анализ деградаций   |
| ERROR     | 90 дней       | Инциденты и разборы |

Ротация индексов - ежедневно. Старые индексы удаляются автоматически

## Превращение логирования в систему анализа

### Алертинг

Алерты на:
- резкий рост ERROR по системе
- отсутствие сообщений из RabbitMQ > N минут
- аномальный рост создания заказов
- расчёт стоимости > SLA (например, 30 минут)

Интеграция алертов:
- Slack / Email
- тикет в Jira

### Поиск аномалий

Использовать:
- rate-based алерты
- пороговые значения
- корреляцию по order_id

## Критерии выбора технологии логирования

| Критерий         | OpenSearch     | ELK             | Splunk        |
| ---------------- | -------------- | --------------- | ------------- |
| Лицензия         | Apache 2.0     | Elastic License | Проприетарная |
| Стоимость        | Низкая         | Средняя         | Очень высокая |
| Vendor lock-in   | Нет            | Да              | Да            |
| Масштабирование  | Горизонтальное | Горизонтальное  | Ограниченное  |
| Kubernetes-ready | Да             | Да              | Частично      |

OpenSearch оптимален для растущей системы с ограниченным бюджетом и планами на Kubernetes
