# Задание 2. Мониторинг

## Мотивация

### Текущая ситуация

1. Данные Яндекс.Метрики покрывают только B2C-трафик сайта
2. Нет видимости работы API для B2B-партнёров
3. Нет мониторинга внутренних систем (CRM, MES, RabbitMQ)
4. Проблемы обнаруживаются только по жалобам клиентов
5. Невозможно диагностировать корневые причины сбоев

### Что даст мониторинг бизнесу

1. Снижение потери доходов - раннее обнаружение проблем с B2B-заказами
2. Улучшение клиентского опыта - проактивное решение проблем до жалоб
3. Повышение операционной эффективности - быстрая диагностика инцидентов
4. Обоснование инвестиций в инфраструктуру - data-driven решения о масштабировании
5. Снижение риска потери контрактов - гарантированное выполнение SLA для партнёров

## Выбор подхода к мониторингу

### Для приложений (ShopAPI, CRM, MES) - "Четыре золотых сигнала" или RED

### Для инфраструктуры (базы, очереди, серверы) - USE

## Метрики для отслеживания

### Группа 1: RabbitMQ

| Метрика                                            | Зачем нужна                                           | Ярлыки (labels)                 |
| -------------------------------------------------- | ----------------------------------------------------- | ------------------------------- |
| Number of dead-letter-exchange letters in RabbitMQ | Показатель потери сообщений. Критично для B2B заказов | queue_name, routing_key, reason |
| Number of message in flight in RabbitMQ            | Показатель накопления очереди, задержек обработки     | queue_name, consumer            |
| Дополнительно: Message publish rate                | Интенсивность нагрузки от CRM                         | exchange, routing_key           |
| Дополнительно: Message consumption rate            | Скорость обработки MES                                | queue, consumer                 |

### Группа 2: Приложения (ShopAPI, CRM, MES)

| Метрика                                        | Зачем нужна                      | Ярлыки                        |
| ---------------------------------------------- | -------------------------------- | ----------------------------- |
| Number of requests (RPS) for internet shop API | Нагрузка на B2C канал            | endpoint, method, http_status |
| Number of requests (RPS) for CRM API           | Активность продавцов             | endpoint, method, user_type   |
| Number of requests (RPS) for MES API           | Нагрузка от внешних партнёров    | endpoint, method, partner_id  |
| Response time (latency) for shop API           | UX для клиентов сайта            | endpoint, method, percentile  |
| Response time (latency) for CRM API            | Производительность для продавцов | endpoint, method              |
| Response time (latency) for MES API            | SLA для B2B партнёров            | endpoint, method, partner_id  |
| Number of HTTP 200/500 for APIs                | Доступность и ошибки             | endpoint, method, status_code |

### Группа 3: Ресурсы инфраструктуры

| Метрика                              | Зачем нужна                        | Ярлыки                         |
| ------------------------------------ | ---------------------------------- | ------------------------------ |
| CPU % для всех API и БД              | Утилизация вычислительных ресурсов | service, instance, environment |
| Memory Utilisation для всех API и БД | Риск OOM (Out Of Memory)           | service, instance              |
| Number of connections для БД         | Нагрузка на базы данных, лимиты    | database, user_type            |
| Size of S3 storage                   | Рост объема 3D-файлов              | bucket                         |
| Size of shop db instance             | Рост данных, планирование очистки  | database, table_schema         |
| Size of MES db instance              | Рост производственных данных       | database, table_schema         |


### Группа 4: Метрики не из списка (рекомендуемые)

- MES dashboard load time - время загрузки дашборда операторов
- Orders created per hour - бизнес-активность, рост (channel (b2c/b2b), status)
- Failed orders rate - процент проблемных заказов (failure_reason, channel)
- Price calculations duration - время расчёта стоимости (2-30 мин) (model_complexity, percentile)

## План действий

### Этап 1: Базовая инфраструктура

1. Развернуть Prometheus на отдельном инстансе EC2
- Настроить сбор метрик приложений через exporters
- Настроить Alertmanager для алертинга

2. Развернуть Grafana для визуализации
- Создать дашборды по группам метрик
- Настроить доступ для команды

3. Внедрить Node Exporter на всех серверах
- Базовые метрики ОС (CPU, память, диск, сеть)

### Этап 2: Мониторинг приложений

1. Инструментировать Spring Boot приложения (ShopAPI, CRM)
- Метрики: RPS, latency, errors, JVM metrics

2. Инструментировать MES (C#)
- Метрики расчёта стоимости, обработки заказов

3. Настроить мониторинг RabbitMQ
- Метрики очередей, сообщений, потребителей

### Этап 3: Мониторинг баз данных

1. PostgreSQL exporter для shop и MES БД
- Метрики соединений, запросов, репликации

2. Настроить метрики роста данных
- Автоматические алерты при достижении лимитов

### Этап 4: Бизнес-метрики и алертинг

1. Реализовать сбор бизнес-метрик
- Счётчики создания заказов
- Таймеры обработки заказов
- Статусы производственной цепочки

2. Настроить алерты по приоритетам
- P1: Потеря заказов, недоступность API
- P2: Деградация производительности
- P3: Предупреждения о росте нагрузки

## Показатели насыщенности и алертинг

### Методология определения порогов:

1. Фаза наблюдения (2-4 недели):
- Сбор baseline метрик
- Корреляция с жалобами пользователей
- Анализ паттернов нагрузки

2. Фаза установки порогов:
- Предупредительные: 70% от критического значения (даёт время на реакцию)
- Критические: Значения, при которых были зафиксированы инциденты
- Катастрофические: Значения, приводящие к финансовым потерям

Для наглядности были выбраны и приоритизорованны показатели насыщенности и им были заданы преположительные пороги

### Критические пороги (P1 - немедленное действие)

| Компонент | Показатель              | Порог                    | Действие                                                                |
| --------- | ----------------------- | ------------------------ | ----------------------------------------------------------------------- |
| RabbitMQ  | Dead letters rate       | > 1% от общего трафика   | Автоматический алерт в Slack/Telegram команде, создание тикета P1       |
| RabbitMQ  | Messages in flight      | > 1000 на очередь        | Автоматическое масштабирование потребителей MES (если настроено), алерт |
| MES API   | Response time p95       | > 10 сек                 | Алерт операторам, временное ограничение B2B трафика через rate limiting |
| БД        | Connections             | > 80% от max_connections | Алерт DevOps, создание тикета на увеличение лимитов                     |
| Заказы    | Price calculation queue | > 50 заказов             | Алерт о необходимости увеличения capacity расчёта стоимости             |

### Предупредительные пороги (P2 - действие в течение часа)
