# Задание 3. Трейсинг

## Анализ системы для трейсинга

### Ключевые точки, где заказ может "сломаться" или зависнуть

1. ShopAPI -> CRM (через общую БД)
2. CRM -> RabbitMQ
3. RabbitMQ -> MES
4. MES -> CRM (обратно)
5. CRM -> MES (производство)

### Данные для трейсинга

#### Обязательные поля в трейсе:
1. Trace ID - глобальный идентификатор цепочки
2. Span ID - идентификатор отдельной операции
3. Parent Span ID - связь между операциями
4. Timestamp - время начала/окончания
5. Duration - длительность операции
6. Service Name - название сервиса
7. Operation Name - что делалось (например, "calculate_price")
8. Tags/Labels:
- order_id - идентификатор заказа
- user_id - идентификатор пользователя
- channel - b2c/b2b
- status - текущий статус заказа
- model_complexity - полигоны/размер
- partner_id - для B2B
9. Logs - детальные логи операции
10. Errors - флаги и описания ошибок

## Мотивация

### Технические метрики, которые улучшатся

1. Сильно уменьшится среднее время диагностики инцидентов
2. Станет измеримым процент потерянных сообщений RabbitMQ
3. Станет видимым время end-to-end обработки заказа

### Бизнес-метрики, которые улучшатся:
1. Снизится процент заказов с просроченными SLA
2. Уменьшится время выполнения заказа за счёт оптимизаций
3. Улучшится лояльность клиентов (NPS) за счёт прозрачности

## Предлагаемое решение

### Технологический стек:
- OpenTelemetry - стандарт для инструментирования
- Jaeger - основной backend для сбора данных и запросов
- OpenSearch - хранение трейсинга

### Реализация по компонентам:

1. Инструментирование приложений:
- Spring Boot (ShopAPI, CRM): Spring Cloud Sleuth + OpenTelemetry exporter
- C# MES: OpenTelemetry .NET SDK
- RabbitMQ: Пропагация trace_id в headers сообщений

2. Инфраструктура:
- OpenTelemetry SDK и Jaeger Exporter на каждом сервисе (sidecar)
- Jaeger в кластере (Jaeger Collector для сбора, Opensearch для хранения, Jaeger Query и UI для отображения)

### Архитектура алертинга на основе трейсов

#### Реализация:
1. Trace Analyzer:
- Назначение: Анализ трейсов в реальном времени
- Технология: Flink
- Обнаружение:
  - Зависшие заказы (status не меняется > N часов)
  - Аномальная длительность этапов
  - Потерянные сообщения (неполные трейсы)

1. Метрики для алертинга:
- Trace duration p99 > SLA (например, > 1 час для расчёта)
- Error rate по цепочкам (> 5% ошибок в цепочке)
- Trace completion rate (< 95% полных трейсов)

1. Автоматические действия:
- При зависшем расчёте: Перезапуск задачи в MES
- При потерянном сообщении: Повторная отправка из CRM
- При деградации цепочки: Автоматическое масштабирование
- Уведомления в соответсвующую корпоративную внешнюю систему (например: Slack, Email)

## Компромиссы

1. Фронтенд-трейсинг не планируется
- Обоснование: Основные бизнес-проблемы (потеря заказов, зависание расчётов, неясные статусы) происходят в интеграциях между сервисами, а не на клиентской стороне
- Компромисс: Отказ от трейсинга Vue.js приложений в пользу фокуса на бэкенд-системах.

2. Ограниченное внедрение в MES из-за ресурсов
- Обоснование: MES - система на C#, купленная с исходным кодом, но поддерживаемая всего одним разработчиком в команде
- Компромисс: Внедрение трейсинга только в ключевых точках MES вместо полного покрытия (например, инструментирование MES API (точка входа B2B-партнёров))

3. Отказ от трейсинга базы данных на текущем этапе
- Обоснование: Неочевидная ценность при высокой сложности реализации
- Компромисс: Мониторинг медленных запросов через стандартные средства БД вместо полноценного трейсинга

4. Упрощённая интеграция с RabbitMQ
- Обоснование: Сложность инструментирования message broker
- Компромисс: Пропагация trace context через заголовки сообщений без глубокой интеграции

## Аспекты безопасности

1. Аутентификация
- Внедрение OAuth 2.0 с JWT токенами для доступа к Jaeger UI
- Для административного доступа - двухфакторная аутентификация (2FA) с OTP, отправляемым на корпоративную почту

2. Авторизация (RBAC модель)
- Операторы производства - доступ только к трейсам заказов в их смену, read-only режим
- Менеджеры CRM - доступ к трейсам всех заказов, поиск и фильтрация
- Разработчики - полный доступ к трейсам, включая отладочную информацию
- Администраторы системы - доступ к конфигурации и управлению пользователями
- Каждая роль имеет минимально необходимые права

3. Изоляция в защищённом контуре
- Все компоненты трейсинга развёрнуты в изолированной подсети VPC
- Сетевые политики ограничивают входящие соединения только с доверенных IP-адресов офиса

4. Дополнительные меры защиты
- Автоматическое удаление конфиденциальных данных из трейсов (номера карт, персональные email)
- Все запросы к API Jaeger логируются с привязкой к пользователю
- Регулярный аудит прав доступа и активных сессий
