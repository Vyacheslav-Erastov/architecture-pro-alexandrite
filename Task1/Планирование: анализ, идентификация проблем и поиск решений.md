# Задание 1. Анализ, идентификация проблем и решений, планирование

## Идентификация проблемных мест

1. MES долго загружает первую страницу с дашбордом заказов, несмотря на пагинацию
2. Долгий расчёт стоимости занимает 2-30 минут, блокируя MES из-за этого заказы быстро накапливаются
3. Нет кэширования для часто запрашиваемых данных (статусы заказов, списки заказов)
4. Возможное отсутствие или неполнота механизмов гарантированной доставки и повторной обработки в интеграции через RabbitMQ
5. Не решив проблемы с B2C был запущен B2B сегмент, что только усугубило ситуацию
6. Ручное тестирование тормозит релизы - баги high/highest блокируют деплой
7. Отсутствие автоматизации тестирования E2E-сценариев
8. Ручной деплой в release и prod окружения
9.  Отсутствуют механизмы наблюдаемсоти для выявления проблем на ранних стадиях
10. Прямая связь CRM-MES через RabbitMQ без буферизации при высоких нагрузках
11. Операторы не видят актуальные новые заказы из-за медленной загрузки

## Инициативы, которые необходимы для устранения нежелательных ситуаций

1. Внедрить базовый мониторинг и алертинг - Prometheus + Grafana для метрик приложений и RabbitMQ
2. Настроить централизованное логирование - ELK Stack или аналоги для сбора логов всех компонентов
3. Аудит и улучшение RabbitMQ интеграции - проверить/добавить DLQ, retry политики, persistent messages
4. Вынос расчёта стоимости в отдельный пул обработчиков - чтобы не блокировать основной MES
5. Внедрение кэширования Redis - для дашборда MES, статусов заказов
6. Создание API для отслеживания статуса заказа и уведомлений клиентов
7. Добавление read-реплик БД - разделение нагрузки чтения/записи
8. Внедрение балансировщиков нагрузки для всех сервисов
9.  Рефакторинг MES на микросервисы или выделение сервиса расчёта стоимости
10. Горизонтальное масштабирование приложений - возможность запускать несколько инстансов
11. Внедрение паттернов Backpressure и Circuit Breaker для контроля потока и обеспечения отказоустойчивости в интеграции CRM-MES через RabbitMQ
12. Автоматизация E2E тестирования - передать QA инженеру или нанять автоматизатора
13. Настройка полноценного CI/CD pipeline с автоматическим деплоем в release


## Инициативы в порядке приоритета

### Критерии приоритизации:

1. Остановить потерю денег - B2B контракты, потерянные заказы
2. Восстановить контроль над системой - мониторинг, диагностика
3. Устранить самые болезненные точки (MES)
4. Подготовка к росту нагрузки

#### Остановить потерю денег - B2B контракты, потерянные заказы

1. Аудит и улучшение RabbitMQ интеграции - прямо решает проблему потери заказов партнёров
2. Внедрение паттернов Backpressure и Circuit Breaker - предотвращает лавинообразные сбои и потери при пиках
3. Внедрение кэширования Redis - уменьшает нагрузку, снижая вероятность сбоев

#### Восстановить контроль над системой - мониторинг, диагностика

1. Внедрить базовый мониторинг и алертинг - фундамент для любого управления
2. Настроить централизованное логирование - необходимо для диагностики проблем
3. Настройка полноценного CI/CD pipeline - контроль над процессами доставки

#### Устранить самые болезненные точки (MES)

1. Внедрение кэширования Redis - немедленно улучшит загрузку дашборда MES
2. Вынос расчёта стоимости в отдельный пул - разгрузит MES для операторов
3. Создание API для отслеживания статуса заказа - снимет нагрузку с операторов по статусам

#### Подготовка к росту нагрузки

1. Добавление возможности горизонтального масштабирования
2. Внедрение балансировщиков нагрузки
3. Добавление read-реплик БД - масштабирование хранилища данных


### Целевая архитектура через полгода

Через полгода система должна обеспечивать контроль, стабильность и предсказуемость при текущей нагрузке.
За полгода с текущей командой (8 человек + задачи поддержки) можно качественно сделать 2-3 крупные инициативы.

1. Полная Observability
2. Устойчивая интеграция CRM-MES
3. Оптимизированная производительность MES

### 3 инициативы на полгода

1. RabbitMQ аудит + Redis кэширование для максимально быстрого воздействия - останавливаем потерю заказов и разгружаем MES
2. Мониторинг + логирование - без observability все остальные улучшения делаются вслепую
3. Вынос расчёта стоимости в отдельный пул - устраняет коренную архитектурную проблему блокировки MES
